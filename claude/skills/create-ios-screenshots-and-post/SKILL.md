# Create iOS screenshots and post to PR

Use this skill when the user wants visual evidence of UI changes posted to a pull request. The goal is to make PR review effortless and leave a permanent visual record of what each change looked like.

**The screenshot tests are disposable.** They are written into the session scratchpad, compiled into a scratch Xcode project generated in the scratchpad, run once, and deleted. They are never written into the repo's `UITests/` directory, never added to the tracked `project.pbxproj` or `project.yml`, and never committed. At the end of the run, `git status` in the repo must show no changes caused by this skill.

## Overview

1. Identify new/changed views in the current unit of work.
2. Write temporary screenshot tests in the scratchpad.
3. Generate a scratch Xcode project (in the scratchpad) that includes those temp tests.
4. Run the temp tests to produce an `.xcresult` bundle.
5. Extract the named screenshot attachments from the bundle.
6. Upload each image to GitHub via the user-attachments endpoint (no repo commit).
7. Post a single formatted comment on the PR.
8. Delete the scratch artifacts and confirm the repo is untouched.

## Prerequisites

- The repo must have a PR open for the current branch, or the user must specify a PR number.
- `gh` CLI must be authenticated (`gh auth status`).
- UI tests must inherit from `BaseUITestCase`, which provides `attachScreenshot(named:)`.
- The project is generated by XcodeGen (`project.yml` at the repo root, `xcodegen` installed). If it is not, use the worktree fallback in Step 3.

## Helper script

The mechanical parts — building the scratch project, extracting screenshots, and cleaning up — are done by `scripts/scratch_project.py`, next to this file (the skill's base directory is printed when the skill loads). It is specific to the Encamera repo, uses only the Python standard library, and every subcommand fails loudly instead of leaving a half-working state:

| Subcommand | What it does |
|---|---|
| `setup --repo R --scratch S` | Builds the symlink mirror of the repo in `S`, copies the shared test plans, creates `S/temp-screenshot-tests/`, and snapshots the repo's git state. Refuses a non-empty `S` or a repo entry whose name collides (case-insensitively) with a scratch name. |
| `generate --scratch S` | Writes the XcodeGen overlay (pinning every target's `INFOPLIST_FILE` to the value in the tracked `project.pbxproj`, plus the temp test dir on `EncameraUITests`), runs `xcodegen`, then compares the scratch project against the tracked one: same targets, identical build settings for every target and configuration, no `Info.plist` copied as a resource, every temp test in the UI test target's sources. Re-run it after editing the tests. |
| `extract --xcresult X --out D` | Exports attachments from the result bundle into `D`, renamed to their `attachScreenshot(named:)` names; prints a JSON list of `{name, file, test}`. Fails if there are none or two share a name. |
| `cleanup --scratch S` | Deletes `S` (symlinks are unlinked, not followed), prunes worktrees, and fails if the repo's git state differs from the `setup` snapshot. |

`setup`, `generate` and `cleanup` all fail if the repo's git status or tracked diff changed since `setup`.

## Scratch layout

Everything this skill creates lives under one directory in the session scratchpad (the scratchpad path from the system prompt — not `/tmp`, not the repo):

```bash
REPO="$(git rev-parse --show-toplevel)"
SCRATCH="<session scratchpad>/ios-screenshots"
SP="python3 -I <skill base dir>/scripts/scratch_project.py"
$SP setup --repo "$REPO" --scratch "$SCRATCH"
```

`$SCRATCH` doubles as a mirror of the repo root (see Step 3), so the project generated there resolves every repo-relative path exactly as the real one does.

| Path | Contents |
|---|---|
| `$SCRATCH/<repo entry>` | Symlink to each top-level repo entry except `Encamera.xcodeproj` and `.git` |
| `$SCRATCH/temp-screenshot-tests/` | Temp `*.swift` screenshot tests (a real directory, not a symlink) |
| `$SCRATCH/overlay.yml` | XcodeGen overlay spec written by `generate` |
| `$SCRATCH/.scratch-state.json` | Repo path and git-state snapshot written by `setup` |
| `$SCRATCH/Encamera.xcodeproj` | Scratch project generated from the overlay (real directory) |
| `$SCRATCH/DerivedData/` | Build products for the scratch project |
| `$SCRATCH/run.xcresult` | Result bundle |
| `$SCRATCH/png/` | Extracted screenshots |
| `$SCRATCH/comment.md` | Composed PR comment body |

## Step 1 — Identify screenshots to capture

Determine the unit of work: diff the current branch against `origin/main` (or the PR base).

```bash
git diff --name-only origin/main...HEAD -- '*.swift'
```

Look at the changed view controllers, SwiftUI views, and screens. Each new or meaningfully changed view needs at least one screenshot of it in the state under review.

Read the existing UI tests and helpers (`UITests/Helpers/`, `BaseUITestCase`) to learn how to launch the app, seed state, and navigate to each screen. Reuse those helpers from the temp tests — do not copy them, and do not edit them.

## Step 2 — Write temporary screenshot tests in the scratchpad

Write one or more `XCTestCase` files into `$SCRATCH/temp-screenshot-tests/`. **Never create or edit files under the repo's `UITests/` directory** — not even temporarily.

Conventions:

- Prefix every class with `TempScreenshot` (e.g. `TempScreenshotMediaInfoUITests`) so it can never collide with a real test class and is obviously disposable.
- Subclass `BaseUITestCase` and use its launch/navigation helpers.
- Use `attachScreenshot(named: "kebab-case-descriptive-name")` — the name describes the screen/state, not the test.
- Place the call after the view is fully loaded and in the state you want to capture (wait on an element with `waitForExistence`, don't `sleep`).
- One screenshot per distinct visual state. Multiple states of the same screen (e.g. empty vs populated) get separate named screenshots.
- These tests exist only to reach a screen and capture it. Keep assertions to what is needed to be sure the screen is actually showing.

`attachScreenshot` is defined in `BaseUITestCase` and uses `XCTAttachment(screenshot: app.screenshot())` with `.keepAlways` lifetime, so screenshots survive passing runs.

Example (`$SCRATCH/temp-screenshot-tests/TempScreenshotMediaInfoUITests.swift`):

```swift
import XCTest

final class TempScreenshotMediaInfoUITests: BaseUITestCase {
    func testMediaInfoDetails() throws {
        launchApp()
        // navigate to the screen using existing helpers...
        app.cells.firstMatch.tap()
        XCTAssertTrue(app.navigationBars["Info"].waitForExistence(timeout: 5))

        attachScreenshot(named: "media-info-detail-view")
    }
}
```

## Step 3 — Generate a scratch Xcode project

Generate a separate project in the scratchpad that contains every real target plus the temp tests, without regenerating the repo's tracked `Encamera.xcodeproj`.

**Why a symlink mirror.** Build settings and xcconfigs hold paths relative to `$(SRCROOT)` (`INFOPLIST_FILE: ShareExtension/Info.plist`, `CODE_SIGN_ENTITLEMENTS=./Encamera/EncameraDebug.entitlements`, …), and `$(SRCROOT)` is wherever the `.xcodeproj` lives. Generating straight into an empty scratch dir breaks every one of them. Making `$SCRATCH` a symlink mirror of the repo root lets those paths resolve unchanged.

With the temp tests written into `$SCRATCH/temp-screenshot-tests/` (by `setup` in the Scratch layout section), generate the project:

```bash
$SP generate --scratch "$SCRATCH"
```

Do not hand-write the overlay or run `xcodegen` directly; `generate` encodes the fixes for every pitfall below and checks the result. If it fails a sanity check, read its message — do not work around it by editing the scratch `project.pbxproj`.

What it handles, for when something does go wrong:

- **Symlink mirror.** `setup` symlinks every top-level repo entry except `Encamera.xcodeproj` and `.git` into `$SCRATCH`, and `generate` runs `xcodegen` from there. Without it, every `$(SRCROOT)`-relative path in build settings and xcconfigs breaks.
- **Test plans are copied, not symlinked.** `project.yml` references `Encamera.xcodeproj/xcshareddata/TestPlans/Encamera.xctestplan`. A symlinked `xcshareddata` would let `xcodegen` write schemes into the repo.
- **`INFOPLIST_FILE` pins.** In the real repo `xcodegen` auto-detects `Encamera/Info.plist`, but not through a symlinked directory. Unpinned, the plist is copied as a resource and the build fails with "Multiple commands produce .../Info.plist". `generate` copies every target's `INFOPLIST_FILE` from the tracked `project.pbxproj`, so new targets are covered too.
- **Overlay settings style must match `project.yml`.** Some targets write `settings:` as a flat map, others as `settings: base:`. XcodeGen ignores flat keys once a `base:` key is present, so a `base:` overlay on a flat target silently drops all of that target's settings (`GENERATE_INFOPLIST_FILE`, `DEVELOPMENT_TEAM`, entitlements, …). `build-for-testing` still succeeds; the run then fails with "Embedded binary's bundle identifier is not prefixed with the parent app's bundle identifier". `generate` writes each pin in the target's own style, and its full build-settings comparison catches any drift.
- **Case-insensitive filesystem.** The temp test dir is `temp-screenshot-tests/`; a dir called `tests/` would shadow the repo's `Tests/` and its symlink would silently go missing. `setup` refuses any such collision.
- **Overlay merge.** XcodeGen merges the overlay's `sources` with the included target's, so `EncameraUITests` keeps `UITests/` (and `BaseUITestCase`), its `dependencies: [Encamera]` and `TEST_TARGET_NAME: Encamera`, and gains the temp tests.
- The repo's `preGenCommand` (`python3 Scripts/generate_device_mapping.py`) runs from `$SCRATCH` through the `Scripts` symlink; its output is unchanged on a normal run, and the repo guard fails `generate` if it ever does change something.

**Fallback when the project is not XcodeGen-generated:** create a detached worktree inside the scratchpad, add the temp tests and project-file edits there, run from it, and remove it afterwards. The worktree is never committed to and never pushed.

```bash
git -C "$REPO" worktree add --detach "$SCRATCH/worktree" HEAD
# copy $SCRATCH/temp-screenshot-tests/*.swift into the worktree's UI test folder and add them to the target there
# ... run Step 4 with -project "$SCRATCH/worktree/<App>.xcodeproj" ...
git -C "$REPO" worktree remove --force "$SCRATCH/worktree"
```

## Step 4 — Run the temp tests

Run only the temp test classes, against the scratch project, with build products and the result bundle in the scratchpad:

```bash
xcodebuild test \
  -project "$SCRATCH/Encamera.xcodeproj" \
  -scheme EncameraUITests \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=latest' \
  -derivedDataPath "$SCRATCH/DerivedData" \
  -only-testing "EncameraUITests/TempScreenshotMediaInfoUITests" \
  -resultBundlePath "$SCRATCH/run.xcresult" \
  2>&1 | xcpretty
```

The app's deployment target is iOS 26, so the simulator must run iOS 26 or later — older runtimes fail with "doesn't match Encamera.app's iOS Simulator 26.0 deployment target". `xcrun simctl list devices available` shows what is installed. Prefer `id=<UDID>` over `OS=x.y`: an `OS=26.4` specifier does not match a 26.4.1 runtime.

Pass one `-only-testing` flag per temp class. Delete any existing `$SCRATCH/run.xcresult` before re-running — `xcodebuild` refuses to overwrite it.

Confirm the tests passed before proceeding. If a temp test fails, fix the temp test (or the navigation in it) and re-run — do not skip the screenshot. If it fails because the app itself is broken, stop and tell the user rather than capturing a broken state.

## Step 5 — Extract screenshots from the xcresult bundle

```bash
$SP extract --xcresult "$SCRATCH/run.xcresult" --out "$SCRATCH/png"
```

This runs `xcresulttool export attachments`, renames each file to its `attachScreenshot(named:)` name (e.g. `$SCRATCH/png/media-info-detail-view.png`), and prints a JSON list of `{name, file, test}` to correlate screenshots with features. It fails if the bundle has no attachments or two share a name.

## Step 6 — Upload images to GitHub

**NEVER commit screenshots to the repository.** Use GitHub's user-attachments upload endpoint, which is token-authenticated and works on private repos:

```bash
GH_REPO="EncameraApp/Encamera"  # or derive from `gh repo view --json nameWithOwner -q .nameWithOwner`
REPO_ID=$(gh api "repos/$GH_REPO" --jq .id)

upload_image() {
    local file="$1"
    local name=$(basename "$file")
    local url
    url=$(curl -s "https://uploads.github.com/user-attachments/assets?name=$name&content_type=image/png&repository_id=$REPO_ID" \
        -X POST \
        -H "Authorization: Bearer $(gh auth token)" \
        -H "Accept: application/json" \
        --data-binary "@$file" | python3 -c "import sys,json; print(json.load(sys.stdin)['url'])")
    echo "$url"
}
```

Call `upload_image` for each screenshot and store the returned URL.

**Verification**: on a private repo, an unauthenticated curl of the URL returns 404 — that is expected. The URL will render correctly in the PR comment for anyone with repo access.

## Step 7 — Post the PR comment

Compose a single comment containing all screenshots. Use this format for each screenshot section:

```markdown
### <Screen Name / Feature>
<commit SHA link(s) — the commits that introduced or changed this screen>

<Brief description: what was done, what changed, what to look at during review>

<img src="<uploaded-image-url>" width="330" />

<Device the screenshot was taken on, e.g. "iPhone 16 Pro — iOS 18.2 Simulator">

---
```

Repeat for each screenshot. The `---` separator goes between sections, not after the last one.

### Composing the commit links

For each screenshot, identify which commit(s) in the PR introduced or changed the relevant view. Link them as:

```markdown
[`abc1234`](https://github.com/EncameraApp/Encamera/commit/abc1234), [`def5678`](https://github.com/EncameraApp/Encamera/commit/def5678)
```

Use `git log origin/main..HEAD --oneline -- <relevant-file-paths>` to find the right commits.

### Posting the comment

Write the body to `$SCRATCH/comment.md` and post it:

```bash
PR_NUMBER=<number>
gh pr comment "$PR_NUMBER" --body-file "$SCRATCH/comment.md"
```

## Step 8 — Clean up

Delete the scratch directory and confirm the repo is exactly as it was before the skill ran. Use the script rather than `rm -rf` by hand — a trailing slash or a symlink-following option on the mirror would reach into the repo:

```bash
$SP cleanup --scratch "$SCRATCH"
```

`cleanup` removes the mirror without following its symlinks, prunes worktrees, and exits non-zero (listing the changed paths) if the repo's git state differs from the `setup` snapshot.

If `git status` shows anything this skill created (a `TempScreenshot*` file, a changed `project.pbxproj`, a stray `.xcresult`), remove it — never commit it.

## Target override

By default, screenshots are posted as a PR comment. The user may request a different target:

- **Artifact**: publish as a Claude Code artifact instead of a PR comment. Use the same markdown format.
- **Local file**: write the composed markdown to a file the user specifies.
- **Slack**: if the user asks for Slack, post using the format-slack-message skill conventions.

## Anti-patterns

- **Writing screenshot tests into the repo.** Never add or edit files under `UITests/`, and never regenerate the tracked `Encamera.xcodeproj` to include temp tests. The tests live in the scratchpad and die with it.
- **Adding `attachScreenshot` calls to existing tests.** That is a repo change. Write a temp test that navigates to the same screen instead.
- **Committing anything.** Not the temp tests, not the project file, not the screenshots. Use the upload endpoint for images.
- **Using `/tmp` or the repo for intermediates.** Everything goes under `$SCRATCH` in the session scratchpad.
- **Posting one comment per screenshot.** Always batch into a single comment.
- **Screenshots of unchanged screens.** Only capture what's new or changed in this unit of work.
- **Unnamed screenshots.** Every `attachScreenshot` call must have a descriptive name — `screenshot-1` is not acceptable.
- **Skipping failed tests.** If a temp test fails, fix it. A screenshot of a broken state is not useful evidence.
